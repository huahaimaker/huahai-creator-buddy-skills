# 小红书正文写作

把用户真实有的材料变成读得懂、能核对的正文。自然语气来自具体事实和原话，不靠伪造经历、故意错别字或堆 emoji。

标题矩阵交给 `huahai-space-xhs-title`；发布后数据归因交给 `huahai-space-xhs-note-analytics`。

## 1. 先判交付状态

只允许三种状态：

| 状态 | 条件 | 交付 |
| --- | --- | --- |
| `publishable` | 核心经历、数字、对象和风险主张都有来源 | 可发布稿 + 核验表 |
| `needs_confirmation` | 主体够写，但少量关键字段待确认 | 带清晰占位符的核验稿 |
| `scaffold` | 只有主题，或第一人称体验/结果严重缺失 | 结构、问题清单和示例句式，不伪装成成稿 |

用户说“直接写”不等于授权补造事实。

## 2. 建事实台账

将素材拆成原子事实，并保留来源：

| id | 类型 | 内容 | 来源 | 置信状态 |
| --- | --- | --- | --- | --- |
| F1 | 经历 | 转行第 4 个月 | 用户原文 | confirmed |
| F2 | 数字 | 投递 47 份 | 用户原文 | confirmed |
| F3 | 结果 | 状态好多了 | 用户原文 | confirmed-subjective |
| F4 | 细节 | 面试官说了某句话 | 未提供 | missing |

必须盘点：

- 谁经历了什么，时间和场景是什么；
- 用户实际做过的动作；
- 已发生的结果、数字和观察窗口；
- 用户原话与可改写边界；
- 产品或服务是否真的使用过；
- 是否为商业合作；
- 医疗健康、收益、未成年人、品牌对比等风险；
- 图片、后台或外部来源能证明什么，不能证明什么。

把品牌 brief、公开资料、用户亲身体验分成不同来源，不相互替代。

## 3. 声明台账

正文里每个可核验主张都要能回指事实：

| claim | fact_refs | 状态 | 处理 |
| --- | --- | --- | --- |
| “投了 47 份简历” | F2 | supported | 保留 |
| “三天治好闭口” | brief-only | reject | 删除疗效主张 |
| “很多人都这样” | none | reject | 删除或改为用户自身范围 |

以下内容无来源时一律不写：

- 时间、价格、收入、涨粉、节省比例、排名；
- “亲测、回购、一直在用、朋友都说”；
- 职业、学历、年龄、城市、肤质、家庭关系；
- 对话、他人反应、失败细节、使用感受；
- 医疗功效、收益保证、绝对化比较和因果结论。

可以压缩、排序和口语化 confirmed 事实，但不能让改写后的主张更强。

## 4. 选择结构

按已有素材选择，而不是按用户想要的标签硬套。

### 教程

需要：可复现步骤、适用条件、每步动作和验证标准。

结构：读者问题 → 前提 → 步骤 → 易错点 → 如何判断做对了。

若只有方法名没有步骤，交付 scaffold。

### 个人经历

需要：真实场景、动作、转折与现在状态。

结构：一个已发生的具体场景 → 当时问题 → 实际动作 → 结果 → 用户自己的理解。

不要补“面试官一句话点醒我”“朋友都不理解”等戏剧性细节。

### 测评或种草

需要：确实使用过、使用时长、场景、可观察体验和限制。

结构：为什么尝试 → 使用条件 → 观察 → 不适用情况 → 主观结论。

没有实测只能整理资料或写待填模板，不能用第一人称测评口吻。

### 清单或合集

需要：实际条目和筛选标准。

结构：适用对象 → 筛选口径 → 每项差异 → 怎么选。

标题和正文条目数必须一致。

### 避坑

需要：真实踩坑或可验证的通用检查项。

结构：风险场景 → 发生了什么 → 如何检查 → 适用边界。

没有可靠证据时不点名指控品牌或个人。

### 经验复盘

需要：起点、动作、窗口、结果和混杂因素。

结构：目标 → 做了什么 → 哪些数据可比 → 观察 → 不能证明什么 → 下一轮实验。

## 5. 写作规则

### 开头

前几行先给读者一个真实锚点：问题、场景、已发生结果或适用对象。不要虚构数字来制造钩子。

### 正文

- 一段只讲一件事，按手机阅读节奏自然分段；
- 具体名词和动作优先于空泛形容词；
- 关键步骤用序号；
- 不强制固定字数、固定 emoji 密度或网络流行语；
- 用户有稳定语气样本时优先对齐；没有时使用自然、克制的中文；
- 不故意加入错别字、口头禅或“真实缺点”来伪造人感。

### 结尾

教程可给下一步，经历可给一个具体问题，测评可说明适用边界。不要机械要求点赞收藏关注，也不编造“评论区扣 1 发资料”。

### 标签

标签必须来自正文真实对象、场景和人群。默认给 3–6 个候选，并说明发布前在客户端确认是否仍适用；不声称标签大小、流量等级或推荐权重。

## 6. 商业与高风险内容

商业稿先分三列：品牌必须表达、用户确实体验、尚待证明。品牌给出的功效或比较结论不能自动进入第一人称体验。

遇到以下情况：

- 医疗、疾病、药品和治疗效果：不替换近义词绕开审核；删除无证据功效并建议专业核验；
- 收益、投资、就业承诺：写清个人样本、时间和条件，不保证复制；
- 点名负面评价：只保留有证据的事实和明确的主观体验；
- 广告标识、平台规则或法律要求：提示按发布时适用规则核验，不编造当前规则。

若删掉高风险主张后素材不足，状态降为 `needs_confirmation` 或 `scaffold`。

## 7. 输出格式

### 交付状态

`publishable / needs_confirmation / scaffold`，并用一句话说明原因。

### 事实台账

列出 F1...Fn、来源和缺失项。内容很短时可压缩，但不能省略缺口。

### 正文

- `publishable`：给完整正文；
- `needs_confirmation`：使用 `【待确认：具体内容】`，不要用看不出的暗占位；
- `scaffold`：给段落目标、需要回答的问题和一两个不含虚构事实的句式示例。

### 声明核验

| 主张 | fact_refs | 状态 |
| --- | --- | --- |

只列数字、效果、身份、价格、比较、经历等关键主张。

### 发布前检查

- 需要用户确认的字段；
- 商业或高风险事项；
- 适用边界；
- 可选工作标题和 3–6 个标签。

## 8. 改写既有正文

1. 先锁定不得改动的事实、数字和原话；
2. 标出原稿中新增但无来源的主张；
3. 只改结构、句序、冗余和语气；
4. 输出“保留 / 删除 / 待确认”差异摘要；
5. 不把用户原本克制的表达自动改成夸张网感。

## 9. 失败处理

| 情况 | 处理 |
| --- | --- |
| 只有主题 | scaffold |
| 要求虚构亲测或身份 | 拒绝虚构，给第三人称资料框架或待填模板 |
| 关键数字互相冲突 | 列出冲突，不擅自选一个 |
| 图片/链接读不到 | 说明未验证，要求粘贴关键内容 |
| 素材可写但少一个字段 | needs_confirmation |
| 标题需要多版 | 路由到 title Skill，并交接事实台账 |

## 10. 反例黑名单

- 不冒充“每天刷、每周发”的真人作者。
- 不为“像真人”强制添加缺点、emoji、错别字或网络梗。
- 不把品牌 brief 改写成个人体验。
- 不把占位稿标为可直接发布。
- 不凭空生成标签热度、平台机制或合规结论。
- 不引用仓库中不存在的 Skill。

行为回归见 `test-prompts.json`。
